# 검증 3중 게이트 - 만든 사람이 만든 것을 검사하지 않는다

> 카피 초안과 정량 출처 승인 뒤에 게이트 1·2, 이미지 검수와 HTML 조립 뒤에 게이트 3을 진행한다. 앞 게이트가 FAIL이면 뒤로 가지 않는다. 결과는 `sangse/{slug}/qa/`에 남기되 텍스트 초안 PASS, 이미지 검수, 게시 준비를 구분한다. 초안 PASS는 실제 인증·효능·심의나 이미지의 검증이 아니다. 가상 상품은 모든 시연 검사를 통과해도 실제 판매용 검증 완료나 게시 준비 완료로 표시하지 않는다.

## 게이트 1 - 자동 검사 (결정론적, 코드가 판정)

```bash
python3 ${CLAUDE_PLUGIN_ROOT}/skills/sangse/scripts/check_cuts.py "sangse/{slug}" --category {common|food|health_food|cosmetics ...} --platform {web|smartstore|kmong}
# 문단형 copy.md(웹 랜딩 호환 모드)는 check_copy.py
```

컷 시트 검사 항목: T1 컷 헤딩·템플릿·높이 / T2 헤드 행 수·행당 글자·본문 줄 수·줄당 글자(44종 템플릿 한도) / T3 컷 수 10~20·Q1~Q8 커버리지·순서 / T4 팩별 첫 컷·bg·K4 각주·K7 고시 문구 / T5 정량 문장 출처 연결(cuts+legal) / T6 금지어 / T7 legal 필수 블록 / T8 스타일 팩 시퀀스(style 지정 시) / I 이미지 실존·폭≥900 / P 플레이스홀더 정보. I의 파일·해상도 확인은 이미지 내용 검수가 아니다. 아래 C1~C10 표는 문단형 레거시 기준이며 T5의 승인 계약과 혼동하지 않는다.

**게이트 1 전 정량 승인**: [numerical-provenance.md](numerical-provenance.md)의 계약을 따른다. 숫자·단위가 입력 어딘가에 있다는 것만으로는 충분하지 않다. 정량 필드 전체 또는 legal 행/문장이 완전한 입력 문장과 일치해야 하며, 재서술은 intake의 `quantitative-facts` JSON에서 위치별로 승인한다. `at`은 `C07.body` 같은 필드 또는 `legal:정확한 섹션 제목`, `claim`은 본문 줄바꿈을 포함한 필드 전체 또는 legal 행/문장 전체, `sources`는 `file`과 정확한 `quote` 목록이다. 출처는 `raw-input.md`·`intake-checklist.md`만 허용한다. 인용문은 승인 블록 밖에 실제로 존재해야 한다.

사람이 대상·속성·수량·단위·섭취 기준·조건·기간을 대조한 뒤 승인한다. 파생 단가·총량·기간에는 원래 입력 수치, 계산식, 단위, 반올림 기준을 남기고 계산 자체도 사람이 확인한다. T5는 인용과 승인 무결성 검사이지 산술 검증이나 의미·진실성 증명이 아니다. 출력 문장을 자동으로 승인 목록에 복사해 FAIL을 없애지 않는다. 수정된 카피·출처·계산은 다시 검토한다.

| ID | 판정 | 실패 시 |
|---|---|---|
| C1 | Q1~Q8 헤딩 8개, 순서 | 헤딩 수정 |
| C2 | Q1에 첫 화면 금지어("AI 기반", "국내 최초", "올인원", "누구나") 없음 | Q1을 고객 장면으로 다시 |
| C3 | copy.md의 모든 숫자가 raw-input/intake에 존재. 파생 수치는 intake에 `파생: 300 mL = 10 mL × 30포` 계산식 필요 | 숫자 삭제 또는 출처 기록 |
| C7 | 헤드라인 20자 이내 | 줄이기 |
| C8 | CTA 3개 이상·문구 동일·행동+결과 | CTA 통일 |
| C9 | `assets/banned-words.json` 카테고리 금지어 없음 (ban=FAIL, warn=WARN) | compliance.md 치환표로 번역 |
| C10 | Q6 사양 표, 물성 플랫폼이면 Q7 FAQ | 추가 |
| I | images.json의 파일 실존 | 재생성 또는 `[이미지 생성 실패]` |

exit 0이 아니면 게이트 2로 가지 않는다. WARN은 문맥을 보고 review-log에 판단 이유를 한 줄 남긴다. 산출은 컷 모드 `qa/check_cuts.json`, 문단형 레거시 모드 `qa/check_copy.json`이다.

## 게이트 2 - 고객 시뮬레이션 리뷰 (에이전트 4인 병렬, 작성자와 분리)

카피를 쓴 Claude가 아니라 **별도 에이전트 4개**가 컷 모드의 `cuts.md`·`legal.md`·`raw-input.md`·`intake-checklist.md`를 보고 판정한다. `copy.md`는 문단형 레거시 모드에서만 사용한다. 프롬프트 골격은 §5. 4개를 한 메시지에 동시에 스폰한다. 사용자 카피 승인도 같은 모드와 파일 스냅샷을 대상으로 한다.

리뷰·승인 보고마다 검토 일시, 모드, 플러그인/스크립트 버전(미커밋 수정이 있으면 스크립트 해시도), 읽은 입력 파일의 경로와 SHA-256을 기록한다. 이미지·렌더 보고에는 승인한 텍스트 스냅샷, 이미지별 경로/SHA-256, index.html과 스크린샷 경로/SHA-256도 남긴다. 자동 JSON에 없는 정보는 리뷰 보고에서 보완한다. 카피·입력·이미지가 바뀌면 관련 검토를 다시 한다. **이전 copy QA는 새 cuts나 교체 이미지의 PASS 근거가 될 수 없다.** 과거 보고는 당시 파일에 대한 역사적 기록으로 남긴다.

| 리뷰어 | 페르소나 | 판정 축 |
|---|---|---|
| 의심 많은 고객 | intake M2의 타겟 그대로(연령·상황·오늘 겪는 장면). "그래서 나한테 뭐가 좋은데?"를 모든 문장에 붙임 | Q1~Q8 각각 **네/아니오** + 아니오의 이유가 되는 문장 인용 + 고객 언어로 재작성 제안 |
| 규제 심사관 | 식약처·공정위 심의 담당자 관점 (`compliance.md` §1~§3·§7 기준) | 위반 의심 문장·조문·수정안. 심의 통과 여부 |
| CRO 리뷰어 | `evidence.md` 기준으로 첫 화면·가독성·CTA·사회적 증거·스펙 유무 채점 | 항목별 1~5점, 근거 |
| 경쟁사 마케터 | 같은 카테고리 경쟁 제품 담당자. 이 페이지에서 가격 비교로 끌어갈 수 있는 틈을 찾음 | "우리라면 이렇게 반박한다" 3개 + 방어 문장 제안 |

**통과 기준**: 의심 많은 고객이 Q1~Q8 전부 "네" + 규제 심사관 위반 0건. 미달이면 지목된 문장만 고쳐 **최대 2라운드** 재리뷰(전면 재작성 금지). 2라운드 뒤에도 "아니오"가 남으면 그 항목을 사용자에게 보고하고 결정을 넘긴다.

Chairman(메인 Claude)이 4개 결과를 `qa/sim-review-r{n}.md`로 합치고, 수정 문장은 `review-log.md`에 `원문 → 수정문 (리뷰어)` 형태로 기록한다.

**리뷰 스탬프와 델타 리뷰.** 리뷰를 마친 카피에 `review_stamp.py <dir> record --review <VERDICT가 있는 리뷰 파일>`로 컷별·legal 섹션별 해시를 남긴다. 그 뒤 사용자 선택(Step 7)이나 형식 수정으로 카피가 바뀌면 `verify`가 바뀐 단위를 나열한다. 그 단위만 규제 심사관·의심 많은 고객에게 전후 대조로 다시 보여 `qa/sim-review-delta-{n}.md`(끝줄 `VERDICT`)를 만들고 다시 `record`한다. 델타 리뷰는 2라운드 상한에 세지 않으며, `verify`가 FRESH가 아니면 이미지 생성과 `assemble_html.py --final`로 가지 않는다. 리뷰 없이 반영한 변경을 "형식 수정이라 생략"으로 넘기지 않는다.

## 게이트 3 - 렌더 검증 + 5초 테스트 (HTML 조립 뒤)

1. 스크립트로 실제 브라우저 렌더 + 계측을 한 번에 한다:
   ```bash
   python3 ${CLAUDE_PLUGIN_ROOT}/skills/sangse/scripts/render_check.py "sangse/{slug}" --widths 390,860 --full
   ```
   Playwright viewport 에뮬레이션으로 `qa/render-390.png`·`qa/render-860.png`(첫 화면)와 `-full.png`(전체)를 저장한다. 가로 스크롤·깨진 이미지와 모드별 위치 계측을 `qa/render_check.json`에 기록한다. 컷 모드의 클로징과 이미지 내부 CTA는 아래 구분을 따른다. 문단 모드에서는 헤드라인과 실제 CTA를 계측한다. FAIL이면 exit 1.
   **함정**: 헤드리스 Chrome CLI(`--window-size=390,…`)는 최소 창 폭이 500px라 390 스크린샷이 오른쪽이 잘린 것처럼 나온다(2026-09-02 실측: `innerWidth=500`). 이걸 레이아웃 결함으로 오판하지 말 것 - 반드시 viewport 에뮬레이션(Playwright·paseo resize)을 쓴다.
2. 스크린샷을 **Read로 직접 본다**(계측 JSON만 믿지 않는다): 이미지 안 한글이 깨지지 않았는가 / 표가 표로 렌더됐는가 / 노란 플레이스홀더가 숨겨지지 않았는가 / 히어로 텍스트가 잘리지 않았는가 / **제품 물리 상태**(미개봉·내용물 노출·포장 결합·개수·손가락)가 정상인가.
   컷 모드에서 render_check는 첫 컷이 화면 상단에 있는지·Q7/Q8 컷 존재·모든 컷의 본문 폭 일치(1px 허용)·미생성 컷 수·가로 스크롤·깨진 이미지를 계측한다. `closingCutPresent`와 `closingCutTop`은 보증·클로징 컷의 존재와 위치이며 클릭 가능한 CTA가 있다는 뜻이 아니다. DOM `.cta`가 없는 이미지 컷에서는 `ctaPositionStatus: manual_review`, `firstCtaTop: null`, `ctaInFirstTwoViewports: null`로 남긴다. 이미지 내부 헤드라인·CTA의 가독성과 위치는 Read로 검수한다. DOM CTA가 있으면 `ctaPositionStatus: measured`와 실제 위치를 기록한다. 문단 모드는 기존처럼 첫 두 화면 안의 실제 CTA를 요구한다.
   **가독성**: HTML 글자는 14px 미만이거나 명암비 4.5:1(24px 이상·18.66px 굵은 글자는 3:1) 미만이면 `textIssues`로 FAIL이다. 이미지에 구운 글자는 픽셀로 판독하지 않으므로 `cutImageScale.px1000For14`(이 폭에서 14px가 되는 폭 1000 환산 px, 브리프와 같은 단위)·`sourcePxFor14`(원본 px)와 대조해 Read로 판정한다. 서브·본문·각주가 그보다 작거나, 밝은 배경 위 회색·연한 글자거나, 사진 위에 바로 올라간 글자면 그 컷을 `image-briefs.md` §3 기준(서브 40·본문 36·각주 30px, #222~#333)으로 재생성한다.
   폭 검사는 컷 바깥 요소와 내부 이미지 모두에 적용한다. `cutWidthMismatches`는 바깥 요소, `imageWidthMismatches`는 실제 이미지의 불일치다. 바깥 요소만 넓고 이미지가 좁은 경우에도 실패해야 한다.
3. **5초 테스트**: `qa/render-390.png` **1장만** 새 에이전트에 Read 시키고(다른 파일 금지) 세 질문을 던진다 - "무엇을 파는 페이지인가 / 누구를 위한 것인가 / 사면 무엇이 달라지는가". 세 답이 intake의 M1·M2·M4와 맞으면 통과. 하나라도 못 맞히면 첫 컷(앵커)의 헤드·서브·본문을 고치고 재생성한다. 결과는 `qa/five-second.md`.
   - 컷 모드에서 **가격은 판정 항목이 아니다** - 레퍼런스 3채널 모두 가격을 이미지 밖(플랫폼 UI)에 둔다. 문단형(web) 모드에서만 검색 유입 페이지의 첫 화면 가격을 본다.
   - 응답자의 "읽기 어려웠던 부분"은 다음 리비전 후보로 미루지 않는다. 글자 크기·대비 지적은 해당 컷을 재생성하고 5초 테스트를 다시 돌린다. 고치지 못한 지적이 남으면 상태는 "게시 준비"가 아니라 "이미지 검수 미완"이고, 보고에 컷별로 남긴다.
   - 5초 테스트는 앵커 컷 1장의 시험이므로 앵커 생성 직후에 돌려도 된다(뒤 13컷을 만들기 전에 잡는 것이 싸다).
4. 스마트스토어·크몽이면 실제 등록 화면에 붙여 넣기 전 폭(860/720)과 이미지 용량(장당 20 MB 이하, 권장 2 MB 이하)을 확인한다.

## 4. 스코어카드 (실제 결과로 채운다)

아래는 빈 보고 양식이다. 실행하지 않은 항목은 `미실행`, 외부 생성 실패는 `차단/복구 대기`, 검수 전 이미지는 `미검수`로 쓴다. 이미지가 없는 카피 전용 시안도 게시 준비 완료가 아니다. 가상 예시는 게시 준비에 `해당 없음: 가상 시연, 실제 판매용 아님`을 쓴다.

```
| 게이트 | 결과 | 근거 |
|---|---|---|
| 1 자동 검사 | {실제 verdict, fail/warn 수, T5/T8 결과} | qa/check_cuts.json (레거시만 check_copy.json) |
| 2 텍스트 초안 리뷰·승인 | {고객 응답, 규제, CRO, 경쟁 반박, 라운드, 사용자 승인} | qa/sim-review-r{n}.md, 승인 스냅샷 |
| 이미지 검수 | {검수 완료/미검수/교체 대기, 컷별 결과} | 이미지별 경로·SHA-256, 검수 보고 |
| 3 렌더·5초 | {390/860 결과, CTA 계측 또는 manual_review, 5초 응답} | qa/render_check.json, 스크린샷, qa/five-second.md |
| 남은 플레이스홀더 | {실제 수와 항목} | cuts.md + legal.md (레거시만 copy.md) |
| 게시 준비 | {미완료 사유 또는 실제 판매 전 확인 결과; 가상은 해당 없음} | 실물·법정·거래 조건 확인 근거 |
```

스코어카드와 함께 각 리뷰의 입력 파일 경로·SHA-256·버전·일시를 첨부한다. `closingCutPresent`·`closingCutTop`을 실제 CTA 계측으로 바꿔 적거나 `null`을 0/PASS로 해석하지 않는다.

## 5. 리뷰어 프롬프트 골격 (게이트 2)

공통 머리말: "너는 이 상세페이지를 쓴 사람이 아니다. 컷 모드 입력은 {cuts.md}, {legal.md}, {raw-input.md}, {intake-checklist.md}다. 문단형 레거시 모드에서만 cuts.md 대신 {copy.md}를 쓴다. 이 입력과 아래 역할별 기준 문서를 읽고, 문제를 문장 인용과 함께 써라. 정량 승인의 대상·단위·조건과 파생 계산도 검토하라. 검토 파일 경로·SHA-256·모드·버전·일시를 보고 머리말에 기록하라. 판정은 해당 텍스트 스냅샷에 한정하며 실제 이미지나 가상 상품의 실재를 검증했다고 쓰지 마라. 마지막 줄에 `VERDICT: PASS|FAIL`을 적어라."

- **의심 많은 고객**: "너는 {M2 타겟 서술}이다. 오늘 {S1 고민 장면}을 겪었다. 이 페이지를 위에서부터 읽으며 각 섹션 끝에서 '이게 나를 위한 건가 / 뭘 얻나 / 왜 이 방식 / 나도 될까 / 얼마나 힘든가 / 뭘 받나 / 실패하면 / 왜 지금'에 네·아니오로 답하라. 아니오면 그 이유가 된 문장을 그대로 인용하고, 네가 듣고 싶었던 문장을 네 말투로 써라. 표 형식: 섹션 | 네/아니오 | 걸린 문장 | 원하는 문장."
- **규제 심사관**: "너는 {카테고리} 표시·광고 심의 담당자다. compliance.md({경로}) §1~§3·§7 기준으로 위반·위반 의심 문장을 조문 번호와 함께 전부 열거하고 수정안을 써라. 없으면 '위반 없음'이라 쓰되 경계 표현 3개를 골라 근거를 대라."
- **CRO 리뷰어**: "evidence.md({경로})의 기준으로 채점하라: 첫 화면 가치제안(10초 안에 이해되는가) / 가독성(중학생 수준인가) / CTA(행동+결과, 컷 모드는 팩의 클로징·오퍼 배치, 문단형만 조기·반복 CTA) / 사회적 증거(실물 우선, 없으면 정직한 플레이스홀더인가) / 스펙(사양 표 충분한가) / 인식 단계 일치(유입 경로에 맞는 첫 화면인가). 각 1~5점과 근거, 가장 먼저 고칠 1개. 이미지 안 CTA의 실제 위치·가독성은 텍스트만 보고 PASS로 판정하지 마라."
- **경쟁사 마케터**: "너는 {카테고리}에서 더 싼 경쟁 제품의 마케터다. 이 페이지를 읽고 고객을 가격 비교로 끌어갈 수 있는 틈 3개를 찾아 '우리라면 이렇게 말한다'를 쓰고, 각 틈을 막을 방어 문장을 이 페이지 톤으로 제안하라. 없는 사실을 지어내 방어하지 마라."

## 6. 왜 3중인가

- 게이트 1만 있으면 문장이 "맞지만 안 팔리는" 상태를 못 잡는다.
- 게이트 2만 있으면 에이전트가 숫자 출처·금지어를 놓친다. 코드가 먼저 걸러야 리뷰어가 설득력에 집중한다.
- 게이트 3 없이는 이미지 안 한글 깨짐, 첫 화면 밖으로 밀린 헤드라인, 가로 스크롤을 못 본다. 실제 렌더를 본 것만 검증이다.
- 그래도 이 셋은 전부 **출시 전 대리 지표**다. 진짜 검증은 출시 후 A/B다(Step 11의 첫 가설이 그 시작).
